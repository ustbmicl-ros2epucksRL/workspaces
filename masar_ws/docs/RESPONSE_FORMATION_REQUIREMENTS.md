# 响应组可泛化编队重构需求基线

状态：已确认，作为后续改造与回归的稳定需求入口  
适用入口：`run_response_deform_demo.sh`、`run_response_controller_demo.sh`、`run_tepper_response_demo.sh`

## 1. 目标

四台响应机器人以一个虚拟编队中心执行多任务导航，在不同地图和动态交通中保持可观测、可恢复的近似正方形编队，依次完成环绕和运输任务，最后响应显式 HOME 返回运行时初始位姿。实现必须与探索组共存，并保持 ROS1/ROS2 桥接所需的标准 ROS 主站契约。

## 2. 必须满足的行为

1. GUI START 前探索组和响应组均不得产生运动命令；STOP 立即停车但保留可恢复状态；START 恢复原任务阶段。
2. 探索组 HOME 与响应组 HOME 相互独立。响应组完成全部子任务后等待显式 HOME，不自动返航。
3. 响应导航只有一个编队中心规划器、一个路径进度源、一个到达判据和一个最终 `cmd_vel` 发布链。
4. 中心路径必须考虑完整编队包络并偏向通道净空区域。地图缺失直接报错，不生成中心到目标的直线兜底。
5. 编队尺度和局部槽位偏移应由地图净空与实时观测连续决定，不使用固定比例逐档试路；允许短时非严格正方形，但整体中心和槽位身份保持连续。
6. 不使用“领先车硬停”“临近目标强制恢复严格正方形”等堆叠兜底。无路时保留任务状态并依据地图或动态交通变化重新规划。
7. victim/fire 的导航中心为目标物位置；到达后四车执行协调式环绕，各车分别累计至少两圈。环绕半径按可用空间连续缩小，并在空间恢复后回到标称半径。
8. box 的导航目标为推送方向反侧的箱后 staging pose。任务控制切换为同步实体运输：前排接触箱体、后排接触前排，四车形成两条真实力传递链。
9. 箱体到达目标并连续满足保持判据后直接报告 DONE；主链不增加推送完成后的额外脱离状态。
10. 到达判据按任务语义评估中心位置、进度、队形质量和安全状态，不要求四个槽位在同一时刻达到零误差。
11. 响应组对任务路径具有通行优先权；探索组采用单一、渐进的非对称让行约束，禁止双方对同一对象重复避障形成死锁。
12. GUI 任务图必须同时显示机器人—任务连线和具有 frontier/coverage 颜色语义的圆形任务点。

## 3. 泛化与模块边界

- 地图、机器人和箱体差异只通过占据栅格、实时位姿/扫描和物理几何配置表达，算法中不得写入 Tepper 路点或对象坐标。
- 中心规划、净空计算、连续编队、速度安全、任务状态、任务控制和 ROS I/O 分离。
- 更换机器人模型时只需重新测量宽度、长度、扫描自滤半径和动力学限制，不应修改任务状态机。
- 动态机器人不是静态硬墙；全局层使用可衰减交通代价，局部层负责 TTC、优先权和最终实体安全。
- demo 与 Tepper 复用同一生产模块。checkpoint/heuristic 对照入口可以保留，但不得成为并行生产链。

## 4. 启动与桥接契约

- 完整 Tepper 默认使用标准 ROS `11311` 与 Gazebo `11345`；启动前按 ROS 图清理上次运行残留。
- `--shared-master` 仅用于外部桥或编排器已经管理 ROS 图的场景，只检查、不清理，并拒绝双 `/clock`。
- 完整系统不保留换端口规避冲突的第二条入口；独立模块 demo 可以使用隔离测试主站。

## 5. 验收条件

- START 前速度为零；STOP/START 可重复暂停恢复。
- 所有已发现子任务按队列逐个 DONE，无超时伪完成。
- transport 观测到四车实体力传递，并将箱体推送至目标区域后报告 DONE。
- surround 四车各自完成至少 `4π` 角进度，必要时半径可缩小。
- 无响应组内部非任务碰撞，无跨组实体碰撞，无永久对称死锁。
- 响应组 HOME、探索组 HOME 均完成；最终 STOP 后九车保持零速。
- Python、C++ 单元测试、相关 catkin 构建、启动脚本 dry-run 和旧链路引用扫描全部通过。
